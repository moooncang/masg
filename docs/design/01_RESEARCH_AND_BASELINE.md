# 01. 조사 근거와 현재 상태

## 1. 조사 방법과 한계

저장소의 README, GPT_BRIEF, GAME_DESIGN, ASSET_SPEC, LORE와 `src/data/*.js`, `state.js`, `sim.js`, `ui.js`, `main.js`, `render.js`를 확인했다. 원격 지정 브랜치와 로컬 커밋은 일치했다.

외부 자료 확인일은 2026-10-13 한국 시간이다. 아래 공개 저장소의 원문을 직접 읽었다. 장르 사례는 구조 참고이며, 이 게임의 수치는 새로 설계했다. 원본 코드·에셋·문구를 가져오는 제안이 아니다. 열람한 브랜치의 파일은 이후 바뀔 수 있다.

| 실제 열람 자료 | 확인한 사실 | 우리 게임에 적용할 설계 판단 |
|---|---|---|
| [CorsixTH README](https://github.com/CorsixTH/CorsixTH/blob/master/README.md) | Theme Hospital의 재구현임을 명시 | 서비스 업종의 ‘수요→직원·시설→처리→평판’ 구조를 참고할 직접적인 비교 대상 |

Two Point Hospital, Project Hospital, Game Dev Tycoon, Travellers Rest, Recettear의 Steam 공식 설명 조회를 시도했으나 프록시의 HTTP 403으로 열람하지 못했다. 따라서 이번 문서에서는 그 페이지를 읽었다고 주장하거나 해당 게임의 세부 기능을 검증된 근거로 인용하지 않는다. 이용자 리뷰 분석, 실플레이 조사, 시장 규모·판매량 조사는 아직 수행하지 않았다. 위 조사만으로 ‘장기 흥행을 보장한다’는 결론을 내리지 않는다.

## 2. 장르 이해: 경영 시뮬레이션의 재미를 분해

| 층 | 플레이어가 하는 생각 | 필요한 정보 | 실패하는 설계 |
|---|---|---|---|
| 처리 능력 | 방을 늘릴까, 사람을 쉬게 할까? | 방·직원 가동률, 거절·대기 원인 | 광고만 누르면 무조건 이익 |
| 포지셔닝 | 싸고 빠른 가게인가, 전문 예약점인가? | 고객군별 예산·기대·선호 | 가장 비싼 메뉴가 모든 고객에게 최선 |
| 현금 배분 | 지금 투자해도 내일 버틸까? | 운영이익, 현금, 재고, 유지비 | 매출과 순이익이 같은 숫자 |
| 예측과 대응 | 축제를 준비할까, 기존 단골을 지킬까? | 일정, 수요 예고, 계약 조건 | 예고 없이 큰 벌금을 주는 랜덤 사건 |
| 소유감 | 우리 직원과 이 공간은 무엇이 달라졌나? | 경력·단골의 기억·시설 변화 | 수치가 커져도 가게가 똑같이 보임 |
| 장기 조합 | 같은 상권을 다른 운영 방식으로 풀 수 있나? | 전문화·지원실·계약의 교환 조건 | 최종 업그레이드 구매 후 의미 소멸 |

핵심은 ‘지속적으로 새로운 판단’이다. 일일 체크리스트 수를 늘리거나 자동 운영을 불편하게 만들어 플레이 시간을 늘리지 않는다. 이미 익힌 판단은 정책으로 자동화하고, 새 판단은 예고된 상권 변화로 제공한다.

## 3. 현재 구현과 기획의 간극

아래 항목은 코드 열람으로 확인했다. 이번 작업에서는 버그 수정이나 게임 코드 변경을 하지 않는다.

| 현 상태 | 장기 플레이 문제 | 제안 |
|---|---|---|
| 09~24시, 실제 3분/일, 4개 메뉴, 최대 4방 | 성장 축이 빨리 소진 | 시간은 유지, 서비스군·전문화·지원실·주간 계약 도입 |
| 고객 메뉴가 무작위/해금 목록 중심 | 가격·기대·예산에 대한 판단 부족 | 8고객군의 수요·예산·적합성으로 선택 |
| 혈맥 메뉴에 `reservation`은 있지만 예약 장부 없음 | ‘예약제’가 운영 의사결정으로 작동하지 않음 | 방·직원·재료·시간을 함께 잡는 예약 |
| 품질 등급이 가격에 최대 1.5배 적용 | 고품질 반복이 과도한 현금 증가로 연결 | 고지 가격 고정, 품질은 만족·팁·재방문에 반영 |
| 향유가 없어도 감점 후 시술 가능 | 재고 관리를 무시해도 영업 가능 | 필수 재료 부족 시 판매 중지·대체 동의 |
| 사장 우선 배정, 직원이 쉬면 피로 회복 | 능력·숙련·교대 선택이 약함 | 배정 정책·전문화 숙련·예약 보호·휴식 임계값 |
| `stamina` 수치는 존재하나 시술 피로 증가량은 고정 | 표시 능력과 실제 효용 불일치 | 체력을 피로 누적식에 반영 |
| 설명에는 네르의 빠른 성장, 실제 경험치에는 전용 배율 없음 | 캐릭터 특색이 설명에 머묾 | 전용 특성과 UI 근거 명시 |
| 레이나 접수 설명은 인내심, 실제 생성식은 유입×1.15 | 기대한 효과를 이해하기 어려움 | 접수 효과를 수요·응대 중 하나로 명확히 정함 |
| 소문 40이 세르피나 해금 조건, 방음벽은 소문 감소 | 잘 운영하면 이야기를 놓침 | 합법적 인증 루트와 감찰 루트를 병행 |
| `checkStoryEvents`는 한 호출에 한 사건만 반환 | ‘하루 한 개’ 주석과 달리 30분마다 추가 사건 가능 | 유형별 일일 제한과 대기열을 명시 |
| 마감 시 진행 중 시술을 즉시 완료 | 빠른 마감으로 처리 시간을 건너뛸 여지 | 신규 접수만 닫고 진행 건 완료 후 정산 |
| 방 0의 `busy`가 거짓으로 평가되는 피로 회복 조건 | 방별 회복 동작이 달라질 여지 | 점유 판정은 null 여부로 통일하도록 인수 검수 |
| 저장 단일 localStorage 키, 이벤트 모달 상태 미보존 | 확장 시 중복 지급·날짜 건너뛰기 위험 | 버전별 이전, 정산 식별자, 선택 대기 상태 저장 |

설명과 코드의 차이는 ‘환경 설치 실패’가 아니라 후속 구현 시 해결할 제품 명세 항목이다.

## 4. 우리 게임의 고유성

마사지 샵의 테마가 실제 규칙에 연결되어야 한다. 피로 회복과 지속적인 돌봄이라는 업종 특성 때문에 직원에게도 휴식이 필요하고, 같은 손님을 반복해서 만나 경과와 취향을 기억하며, 적절한 설명과 조용한 공간이 시술 기술만큼 중요하다.

판타지 요소는 새로운 경영 요구를 만든다. 원정 귀환은 단기 수요, 마탑 연구는 기록의 정확성, 기사단은 시간 약속, 상단은 계약의 유연성과 안정성의 교환이다. 종족은 외형·대사·설명 선호에 사용하되 특정 종족을 일괄적으로 부유하거나 문제 손님으로 만들지 않는다. 예산과 요구는 직업·개인 취향에서 나온다.

## 5. 추가 조사와 플레이테스트 질문

다음 리서치는 구현 전에 무한히 확대하지 않는다. P0가 동작하면 ‘가게가 막힌 이유를 찾는가’, ‘광고 외의 해법을 고르는가’, ‘단골을 기억하는가’를 관찰한다. 외부 서비스 자료 접근이 가능해지면 위 상용 게임들의 공식 설명과 실제 플레이를 별도로 대조하고, 출처·관찰·우리 해석을 분리해 보강한다.
